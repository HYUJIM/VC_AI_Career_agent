# AWS 배포 체크리스트

로컬 실행·문제 해결은 [서비스 실행 방법](../docs/GETTING_STARTED.md), 프로젝트 소개는 [저장소 README](../README.md)에 있습니다.

예시 구성: FE는 S3+CloudFront, BE·AI는 ECS(Fargate) 서비스, DB는 RDS for PostgreSQL 16. 이번 기본 구성은 자기 도메인 없이 CloudFront 기본 주소(`https://dXXXX.cloudfront.net`)로 서비스하고 `/api/*`를 CloudFront VPC 원본 → 내부 ALB(HTTP:80) → BE로 보냅니다. 그 배포 순서(소셜 로그인은 주소가 나온 뒤 2단계)·ECS 작업 정의 템플릿·CloudFront Function·변수 표는 [deploy/README.md](README.md)와 [deploy/ENV_MATRIX.md](ENV_MATRIX.md)에 있고, 이 체크리스트는 항목별 기준입니다. 아래 `<도메인>`·`<FE 도메인>`은 그 CloudFront 주소(자기 도메인을 붙였으면 그 도메인)입니다. `BE/docker-compose.yml`은 로컬 개발 전용(소스 마운트·`--reload`·root·기본 비밀번호 DB)이라 운영에 쓰지 않습니다. 공개된 비밀번호의 시드 계정(`user001@example.com` 등)도 만들므로 EC2 같은 공개 호스트나 데모 서버에서도 띄우지 않습니다.
인증은 설정과 관계없이 항상 켜져 있습니다(토큰 없는 요청은 401, 예전 `AUTH_REQUIRED` 변수는 없어짐). 모의 발급(FE `/issue` 화면)은 운영 이미지(`APP_ENV=production`)에서 기본으로 꺼져 있으므로, 시연 배포에서 쓰려면 아래 `MOCK_ISSUER_ENABLED=true`를 넣습니다. 운영 이미지에서는 API 문서(`/docs`·`/redoc`·`/openapi.json`)와 BE 단독 테스트용 `GET /api/v1/users/oauth/{google,github,naver}/callback`이 404이고, 신원 VP 검증(`type: identity`)은 꺼져 있습니다.
아래에 나오는 BE 자체 한도(로그인 실패 제한, 검증기 호출 한도와 소셜 로그인(제공자별) 토큰 교환 한도, 배지 검증의 거절 창, 모의 발급의 시도 한도·실패 차단기, DB 연결·AI 동시 호출 상한, 사용자별 AI 묶음 요청 한도, LLM 모드 학습 계획의 시도 창)는 모두 **BE 프로세스(ECS 태스크)마다** 메모리에서 따로 세고 태스크를 다시 시작하면 지워집니다. 태스크가 N개면 전체 한도도 N배가 되고 IP별 제한은 없으므로, IP별 제한은 아래 WAF 규칙으로 둡니다. 여러 태스크가 함께 지키는 한도는 DB로 세는 것(모의 발급의 사용자별·전체 24시간 한도, 포트폴리오·공유 링크 개수, 사용자별 24시간 직무 비교·학습 계획·저장된 LLM 학습 계획 수)뿐입니다.

## 이미지

- [ ] BE·AI 이미지는 같은 커밋으로 만들고(`docker build --platform linux/amd64 -t <ECR 주소>/vc-be:<커밋> BE`, `docker build --platform linux/amd64 -t <ECR 주소>/vc-ai:<커밋> ai`) 함께 배포합니다. 공유 계약 ID가 다르면 직무 비교 API가 502입니다. 되돌릴 때는 다시 빌드하지 말고 이전 이미지 태그를 배포합니다.
- [ ] 두 이미지는 `python:3.11.15-slim-bookworm` 기반, 비루트(uid/gid 10001), `--reload` 없는 uvicorn 한 프로세스이고, 의존성은 `requirements.txt`의 고정 버전입니다. 서비스 작업 정의에서 명령·사용자를 덮어쓰지 않습니다(마이그레이션 태스크만 명령 덮어쓰기). `UVICORN_*` 환경변수는 uvicorn 실행 옵션으로 읽힙니다. 아래 `UVICORN_TIMEOUT_KEEP_ALIVE` 외에는 넣지 않습니다(특히 `UVICORN_RELOAD`는 운영 이미지에서 리로더를 켭니다). BE 이미지의 Python 버전(3.11, 유니코드 14)과 DB 엔진·libc(RDS 엔진 업그레이드 포함)는 함께 맞춰 올립니다: 한쪽만 올리면 로그인 실패 제한이 이메일을 접는 방식이 DB `lower()`와 달라질 수 있고, 그때는 [BE/README.md](../BE/README.md) "로그인 실패 제한"의 예외 동작을 따릅니다.
- [ ] Fargate 기본 플랫폼은 x86_64이고 [deploy/ecs](ecs)의 작업 정의도 `runtimePlatform.cpuArchitecture: X86_64`이므로 위 명령처럼 늘 `--platform linux/amd64`로 빌드합니다(Apple Silicon Mac에서 빼면 arm64 이미지가 되어 태스크가 시작하지 못함. `docker image inspect --format '{{.Os}}/{{.Architecture}}' <이미지>`가 `linux/amd64`인지 확인). ARM64로 가려면 BE 서비스·마이그레이션·AI 작업 정의를 모두 ARM64로 바꾸고 arm64로 빌드합니다.

## BE·AI 환경변수·비밀값

비밀값은 작업 정의의 `secrets`로 Secrets Manager·SSM Parameter Store에서 넣습니다. `.env`는 이미지에 들어가지 않습니다.

- [ ] `APP_ENV=production`: 이미지 기본값이므로 `development`를 넣지 않습니다. 아래 비밀값이 없거나 이 저장소에 공개된 테스트·예시 값(`BE/tests`·`BE/.env.example`의 값, `x`·`0x01` 반복 같은 자리표시 값)이면, 또는 `DB_HOST`·`DB_NAME`·`DB_USER`가 비었거나 `DB_PASSWORD`가 비었거나 로컬 기본값 `password`면, 또는 `JWT_SECRET`·`HOLDER_KEY_ENCRYPTION_KEY`·`SERVICE_API_KEY`·`AI_SERVICE_TOKEN`·`DXWORKS_API_KEY`·`GOOGLE_CLIENT_SECRET`·`GITHUB_CLIENT_SECRET`·`NAVER_CLIENT_SECRET` 중 넣은 두 값이 서로 같으면, 또는 `PGSSLMODE`가 `verify-full`·`verify-ca`가 아니거나 `PGSSLROOTCERT`가 읽을 수 있는 파일이 아니면(아래 "RDS TLS"), 또는 아래 소셜 로그인·`CORS_ORIGINS` 규칙에 맞지 않으면 BE가 시작하지 않습니다. 이때 BE는 traceback 없이 stderr에 `APP_ENV=production requires …` 한 줄(변수 이름만, 값 없음)을 남기고 종료 코드 1로 끝납니다(CloudWatch 지표 필터 `"APP_ENV=production requires"`·`"must be"`). 마이그레이션 태스크도 같은 `DB_PASSWORD`·TLS 규칙으로 접속하지 않고 `마이그레이션 실패:` 한 줄과 종료 코드 1로 끝납니다. 비밀값은 [서비스 실행 방법](../docs/GETTING_STARTED.md) 2번 명령으로 운영용을 새로 만들되, Secrets Manager에는 `JWT_SECRET=`처럼 이름을 붙이지 않고 값만, 끝 줄바꿈 없이 넣습니다([deploy/README.md](README.md) ④).
- [ ] `JWT_SECRET`: 32바이트 이상, 모든 태스크·워커가 같은 값. 다르면 태스크끼리 서로의 토큰을 거절해 FE가 계속 로그인 화면으로 돌아갑니다. 바꾸면 모든 사용자가 한 번 로그아웃됩니다.
- [ ] `JWT_EXPIRES_MINUTES`(선택): 토큰 수명(분). 1~1440 정수만 받습니다(기본 1440, 그 밖이면 BE가 시작하지 않음). 로그아웃하지 않고 떠난 세션(공용 PC 등)이 살아 있는 최대 시간이라 짧을수록(예: 480) 안전하지만 다시 로그인하는 일이 잦아집니다. 로그아웃(`POST /api/v1/users/logout`)은 이 값과 관계없이 그 계정의 토큰을 바로 모두 무효로 만듭니다.
- [ ] `HOLDER_KEY_ENCRYPTION_KEY`: 32바이트 base64, 모든 태스크가 같은 값. 바꾸거나 잃어버리면 기존 홀더 키를 복호화할 수 없습니다. 형식이 틀리면(base64가 아니거나 32바이트가 아님, `HOLDER_KEY_ENCRYPTION_KEY=` 접두사를 붙인 값 등) BE가 `HOLDER_KEY_ENCRYPTION_KEY must be base64`·`HOLDER_KEY_ENCRYPTION_KEY must decode to 32 bytes` 한 줄(값 없음)과 종료 코드 1로 시작하지 않습니다.
- [ ] `AI_SERVICE_TOKEN`: 32바이트 이상, BE와 AI 서비스에 같은 값. `JWT_SECRET`·`HOLDER_KEY_ENCRYPTION_KEY`·`SERVICE_API_KEY`·`DXWORKS_API_KEY`·`GOOGLE_CLIENT_SECRET`·`GITHUB_CLIENT_SECRET`·`NAVER_CLIENT_SECRET`과는 다른 값으로 따로 만듭니다(같으면 BE가 시작하지 않음).
- [ ] `DXWORKS_API_HOST`(`https://` 주소), `DXWORKS_API_KEY`(ASCII 문자만), `DXWORKS_BADGE_TEMPLATE_ID`. 호스트가 `https://` 주소가 아니거나(`http://`는 루프백만) 사용자 정보·쿼리·프래그먼트·공백이 들어 있으면, 또는 키에 ASCII가 아닌 문자가 있으면 BE가 시작하지 않습니다(오류에는 변수 이름만 나옴). 비워 두면 BE는 뜨고 발급·검증·재검증·포트폴리오 생성·직무 비교가 503 `PROVIDER_NOT_CONFIGURED`입니다. `DXWORKS_TIMEOUT_SECONDS`(선택, 기본 15)는 1~120만 받습니다.
- [ ] DXWorks 호출 보호(설정값이 아니라 코드에 고정된 한도이고 태스크마다 따로 셈. 운영자가 넣을 값은 없고, 아래 WAF 규칙과 로그 지표만 준비):
  - 로그인 사용자가 검증기를 부르는 API(`POST /api/v1/verify`, 재검증, 근거 조회, 포트폴리오 생성, 직무 비교)는 부르기 전에 필요한 호출 수(서명 원본 수)만큼 몫을 가져갑니다. 계정마다 분당 120번·시간당 1,200번(서비스 키는 한 몫을 함께 씀), 태스크 전체로 분당 600번이고, 하나라도 모자라면 DXWorks를 한 번도 부르지 않고 429 `Too many verification requests. Try again later.` + `Retry-After`(모자란 몫이 다시 찰 때까지의 시간 중 가장 긴 값)로 답합니다. 시간 몫을 다 쓴 계정은 분당 20번만 부를 수 있어, 태스크 몫(분당 600번)을 계속 비워 두려면 계정이 30개쯤 필요합니다(시간 한도가 없던 때는 6개. 지금도 처음 10여 분은 6개로 가능). 시간당 1,200번은 몫이 다시 차는 속도라, 가득 찬 몫으로 시작하는 계정의 첫 한 시간은 1,200 + 1,200번까지입니다. 새로 가입한 계정도 저마다 가득 찬 몫을 가져오고 BE는 가입 수를 제한하지 않으므로, 아래 WAF의 가입(`/api/v1/users/register`) IP별 규칙도 이 보호의 일부입니다.
  - 배지 검증(`POST /api/v1/verify`)은 DXWorks까지 가서 그 토큰이 거절된 요청을 계정마다 10분에 10번까지만 받습니다(넘으면 DXWorks를 부르지 않고 같은 429). 세는 것은 저장하지 않는 `success: false`(해석할 수 없는 원본, 수신자 없음, 발급자 미확인), 다른 DID에 발급된 배지(403), 다른 사용자가 등록한 배지(409), 그 토큰 하나에 대한 검증기 오류(502), 그리고 DXWorks에 묻는 동안 끊긴 요청입니다. 통과한 검증, 폐기·만료 상태로 저장된 배지, 검증기 장애, DXWorks가 답한 뒤 BE 쪽 문제(DB가 바빠 503 등)로 끝난 요청은 세지 않습니다. 모양만 맞춘 쓰레기 토큰을 계정 하나가 분당 한도만큼 DXWorks로 보내지 못하게 하려는 것입니다.
  - 로그인 없는 공유 링크 조회는 따로 태스크마다 분당 300번입니다(503 + `Retry-After`). 같은 서명 원본은 60초 동안 다시 묻지 않고, 같은 원본을 동시에 여는 조회는 먼저 물은 응답을 함께 기다립니다(`DXWORKS_TIMEOUT_SECONDS`의 4배까지).
  - 동시에 DXWorks로 나가는 요청은 태스크마다 16개까지입니다. 응답 본문은 1 MiB까지이고, 압축은 요청하지 않지만 `gzip`·`deflate`로 온 응답은 전송된 크기와 풀어낸 크기를 각각 1 MiB까지만 받으며 직접 풉니다(그 밖의 압축 방식은 거부). 시간은 교환(연결·전송·본문 수신, 연결 재시도 포함)이 `DXWORKS_TIMEOUT_SECONDS`의 2배까지, 그 전에 동시 호출 자리를 기다리는 시간도 2배까지라 호출 한 번은 최악의 경우 4배(기본 15초면 60초로, ALB 유휴 제한 시간 기본값과 같으므로 아래 "시간 제한"대로 ALB 값을 올려 둠)입니다. 넘으면 그 호출을 실패로 처리합니다(배지 검증·모의 발급은 502, 재검증은 검증기 장애면 502).
  - `token`이 JWT(compact JWS) 모양이 아니면 DXWorks로 보내지 않습니다(배지는 200 `success: false`, 신원은 422). 조각 끝의 `=` 패딩과 SD-JWT 형식(`<jws>~…`)은 받습니다. 배지를 모양 때문에 거절하면 감사 로그 `event=verify_shape_refused`가 남습니다. 검증기 장애(연결 실패·시간 초과·5xx·408·429·401·403·3xx)가 한 번 확인되면 그 요청의 남은 자격증명은 부르지 않습니다.
  - 직무 비교는 재검증 전에 AI 설정과 대상 공고를 먼저 확인하므로, 503 `AI_SERVICE_NOT_CONFIGURED`·404로 끝날 요청은 DXWorks를 부르지 않습니다. AI 묶음 요청 자리(`AI_MAX_CONCURRENCY`)는 재검증을 마친 뒤에 잡습니다(자리를 쥔 채 DXWorks를 기다리지 않으므로, DXWorks가 느리거나 멈춰도 공고 목록·학습자료 검색·커리큘럼이 그 뒤에 서지 않음). 그래서 자리가 없어 503 `AI_SERVICE_BUSY`로 끝난 직무 비교는 그 요청의 DXWorks 호출을 이미 쓴 뒤이고, 그 양은 위 계정별 몫에 묶입니다. 재검증 한 건(`POST /api/v1/credentials/{id}/reverify`)에서 DXWorks가 그 자격증명만 거절하면(400·404·422 등) 502가 아니라 200 `success: false`입니다(502/503은 검증기 장애일 때만).
- [ ] 신원 VP 검증: `IDENTITY_VERIFICATION_ENABLED`는 넣지 않습니다(기본 `false`. 꺼져 있으면 `type: identity`는 DXWorks를 부르지 않고 400 `Identity verification is disabled`). 화면이 쓰지 않는 기능이고, 켜면 사용자가 보낸 값에 회사 API 키가 붙어 DXWorks로 나갑니다.
- [ ] 모의 발급(FE `/issue` 화면, 가입 후 첫 배지): 시연 배포에서 쓰려면 `MOCK_ISSUER_ENABLED=true`를 넣습니다(없으면 발급 화면이 404 `Mock issuer is disabled`). 켜면 BE 시작 로그에 경고가 한 줄 남고, 로그인한 본인 DID에만, `DXWORKS_BADGE_TEMPLATE_ID`(+ 선택 `MOCK_ISSUER_TEMPLATE_IDS`, 쉼표 구분)의 템플릿만(그 밖은 403 `Template not allowed`), 사용자별 24시간 `MOCK_ISSUER_DAILY_LIMIT`건(기본 10)·모든 사용자를 합쳐 24시간 `MOCK_ISSUER_GLOBAL_DAILY_LIMIT`건(기본 200)까지 회사 API 키로 발급합니다(넘으면 429). 가입은 누구나 할 수 있어 계정을 여러 개 만들면 사용자별 한도가 곱해지므로, 전체 한도는 시연 인원 × 사용자별 한도보다 조금 크게만 잡습니다(기본 200은 20명 × 10건이라, 그보다 많은 인원이 쓰면 올림). 429의 문구는 세 가지입니다: 그 사용자의 한도면 `Mock issuance limit reached; try again later`, 전체 한도(모든 사용자를 합친 24시간 발급 수(DB), 또는 실패한 것 없이 한도만큼의 발급 요청이 한꺼번에 진행 중)면 `Mock issuance service limit reached; try again later.`(FE는 "전체 모의 발급 한도(24시간)에 도달했습니다…"로 따로 안내), 협력사 실패가 이어져 발급을 잠시 멈춘 동안이면 `Mock issuance is paused after repeated failures. TLS에는 단기 인증서 모드의 루트 Private CA(태그 `AmazonECSManaged`=`true`, CA 인증서를 설치해 `ACTIVE`, 월 $50 + 인증서 요금)와 ECS 인프라 IAM 역할(`ecsInfrastructureRole` + `iam:PassRole`)이 필요합니다(순서·명령은 [deploy/README.md](README.md) ⑥ "선택지 A 준비"). 비용 때문에 TLS 없이 프라이빗 서브넷·보안 그룹만으로 막는 선택지와 AI를 BE 태스크의 두 번째 컨테이너로 두는 선택지(루프백, Private CA 없음), 그 위험·대가는 [deploy/README.md](README.md) ⑥. 다른 내부망 `http://` 주소(내부 ALB의 HTTP 리스너 등)는 쓰지 않습니다.
  - 그 밖(내부 ALB 등, 자기 도메인과 ACM 인증서가 있을 때): HTTPS 리스너 주소 `https://...`를 넣고 `AI_SERVICE_ALLOW_HTTP`는 넣지 않습니다(기본 false).
- [ ] `SERVICE_API_KEY`는 비워 둡니다(쓰는 서비스가 없고, 넣으면 모든 DID를 읽는 키가 됩니다. 넣는다면 `JWT_SECRET`·`HOLDER_KEY_ENCRYPTION_KEY`·`AI_SERVICE_TOKEN`·`DXWORKS_API_KEY`·`GOOGLE_CLIENT_SECRET`·`GITHUB_CLIENT_SECRET`·`NAVER_CLIENT_SECRET`과 다른 32바이트 이상의 새 임의 값이어야 BE가 시작합니다). `RESEARCHER_USER_IDS`·`CURRICULUM_LLM_USER_IDS`는 필요한 계정 UUID만.
- [ ] `AI_MAX_CONCURRENCY`(선택, 기본 4, 1 이상): BE 태스크 하나가 AI 서비스로 동시에 보내는 공고·학습자료 묶음 요청(공고 목록, 직무 비교, 학습자료 검색, 커리큘럼 계획) 수의 상한입니다. 한 사용자는 그 가운데 동시에 2자리까지만 쥐고 묶음 요청은 분당 30번·시간당 300번까지이며, 넘으면 기다리지 않고 429 `Too many analysis requests. Try again later.` + `Retry-After`입니다(코드에 고정된 값). 요청마다 검토된 공고·학습자료 전체를 실어 보내므로 BE·AI 태스크 메모리에 맞춰 둡니다. 자리가 10초 안에 나지 않으면 AI를 부르지 않고 503 `code: AI_SERVICE_BUSY` + `Retry-After: 5`입니다. 자리는 묶음을 DB에서 읽기 전에 잡으므로, 자리를 기다리는 요청은 묶음을 메모리에 올리지 않습니다. 직무 비교는 DXWorks 재검증을 마친 뒤에 자리를 잡습니다(자리를 쥔 채 DXWorks를 기다리지 않음). 그래서 503 `AI_SERVICE_BUSY`로 끝난 직무 비교도 그 요청의 DXWorks 호출은 이미 쓴 상태입니다(계정별 검증기 호출 몫에 묶임).
- [ ] `LOG_LEVEL`은 넣지 않거나 `INFO`로 둡니다(빈 값도 `INFO`. `DEBUG`·`INFO`·`WARNING`·`ERROR`·`CRITICAL`만 받고, 그 밖의 값이면 BE·마이그레이션 실행기가 `LOG_LEVEL must be one of: …` 한 줄과 종료 코드 1로 끝남). `DEBUG`면 외부 호출마다 전체 URL(비공개 DXWorks 호스트 포함)을 남기는 httpx 로그와 접속 호스트·응답 헤더를 남기는 httpcore 로그가 다시 나옵니다. `WARNING` 이상으로 올리면 아래 "상태 확인·로그"의 감사 로그(`vc-be.audit`, INFO)가 남지 않습니다.
- [ ] AI 서비스는 `AI_SERVICE_TOKEN`(BE와 같은 값)만 필수입니다. LLM 모드(기본 공급자 Google Gemini API)는 [ai/README.md](../ai/README.md) 6번의 `CURRICULUM_LLM_*`와 `GEMINI_API_KEY`(Secrets Manager `vc/ai-llm`, 넣는 순서는 [deploy/README.md](README.md) ⑥ "LLM(Google Gemini API) 켜기"). BE의 `CURRICULUM_LLM_DAILY_LIMIT`(선택, 기본 20, 1 이상)은 허용된 계정 하나가 24시간에 만드는 LLM 모드 학습 계획 수입니다(저장된 LLM 계획은 DB로 세고, 외부 LLM까지 간 실패한 시도도 태스크 메모리로 셈. 넘으면 429 + `Retry-After`). AI의 `CURRICULUM_LLM_MAX_CONCURRENCY`(기본 2)는 AI 태스크의 동시 LLM 생성 수입니다.

## DB 마이그레이션

- [ ] RDS에 `DB_NAME` 데이터베이스를 먼저 만듭니다. 마이그레이션은 그 DB와 테이블을 소유할 계정(마스터 사용자)으로 실행하고, 마스터 사용자는 마이그레이션에만 씁니다.
- [ ] DB 확장은 필요 없습니다. 기본 스키마와 마이그레이션(04~13)은 확장을 만들지 않으므로(`gen_random_uuid()`는 PostgreSQL 13부터 기본 제공) RDS에 `pgcrypto`·`vector` 확장을 만들어 두거나 마이그레이션 계정에 확장을 만들 권한을 줄 필요가 없습니다. 예전 버전으로 만든 DB에 남아 있는 `pgcrypto`·`vector`는 그대로 둬도 됩니다(마이그레이션이 지우지 않고, 앱은 쓰지 않음). 로컬 Compose·CI의 DB 이미지는 그대로 `pgvector/pgvector:0.8.7-pg16-bookworm`입니다.
- [ ] 그 DB를 PostgreSQL 14 이하에서 만들었거나 그 버전에서 업그레이드·복원했다면, 마이그레이션 태스크 전에 마스터 사용자로 그 DB에 접속해 `REVOKE CREATE ON SCHEMA public FROM PUBLIC;`을 한 번 실행합니다(14 이하는 기본으로 모든 역할에 `public` 스키마 CREATE 권한을 주고 업그레이드·복원 뒤에도 남아, 그대로면 마이그레이션이 종료 코드 1). 그다음 같은 `psql` 세션에서 아래 조회를 실행해 결과가 없는지 확인합니다. 그 권한으로 다른 역할이 만들어 둔 함수·연산자 등은 CREATE를 거둬도 남는데, 마이그레이션은 `vc_app`과 그 소속 역할, 기본 제공 역할, 그리고 마스터 사용자·OID 10 말고 `public`에 CREATE 권한이 있거나 DB·`public` 스키마를 소유한 역할이 소유한 객체만 거부하기 때문입니다(둘 다 아닌 보통 역할의 객체는 보지 않음). `TRIGGER` 권한도 거둔 뒤에 그 권한으로 만든 트리거가 남는데, 마이그레이션은 WHEN 조건이 있거나 임시 스키마·위 역할들의 함수를 부르는 트리거만 거부합니다. `REFERENCES` 권한도 거둔 뒤에 그 권한으로 만든 외래 키가 남는데, 마이그레이션은 `REFERENCES` 권한이 남아 있을 때만 그 외래 키를 알려 줍니다. 첫 줄의 `SET`은 이 세션이 `pg_catalog`만 찾게 해, `public`이나 마스터 사용자 이름의 스키마에 심어 둔 함수·연산자(예: 결과를 숨기는 `public.<>(oid, regrole)`)가 조회 중에 마스터 사용자 권한으로 불리지 않게 합니다(조회의 비교도 인자 형을 정확히 맞춤). 조회는 ① `public` 스키마에서 마스터 사용자와 부트스트랩 슈퍼유저(OID 10) 말고 다른 역할(`pg_database_owner`·`pg_monitor` 같은 기본 제공 역할 포함)이 소유한 객체, ② 마스터 사용자 이름의 스키마(기본 `search_path`의 `"$user"`라 마스터 사용자가 직접 접속한 세션에서는 `public`보다 먼저 찾음), ③ `public` 테이블에 `TRIGGER`·`REFERENCES` 권한을 받은 역할(`vc_app`이 이미 있으면 그 계정과 그 소속 역할, `PUBLIC` 포함. 열 단위 `REFERENCES`는 둘째 열이 `<테이블> (<열>)`), ④ `public` 테이블의 트리거(시스템 내부 트리거 제외. 이 앱의 스키마·마이그레이션은 트리거를 만들지 않음. 둘째 열은 `<트리거> on public.<테이블> -> <함수>`, 셋째 열은 그 함수의 소유자, WHEN 조건이 있으면 첫째 열이 `trigger (WHEN)`), ⑤ `public` 밖의 테이블에서 `public` 테이블을 참조하는 외래 키(이 앱의 스키마·마이그레이션은 `public` 안의 외래 키만 만듦. 셋째 열은 그 테이블의 소유자), ⑥ `vc_app`(이미 있으면)이나 `vc_app`이 속한 역할이 소유한 스키마(마이그레이션이 거부)를 보여 줍니다. 결과가 있으면 하나씩 확인해 예상하지 못한 객체·스키마는 `DROP`하고, 필요한 객체는 소유자를 마스터 사용자로 바꾸고(슈퍼유저가 아닌 마스터 사용자가 다른 역할의 객체를 지우거나 소유자를 바꿀 때 `must be owner of ...`가 나오면 아래 RDS 항목처럼 먼저 그 역할의 권한을 받음), `TRIGGER`·`REFERENCES` 권한은 `REVOKE TRIGGER ON ALL TABLES IN SCHEMA public FROM "<역할>";`·`REVOKE REFERENCES ON ALL TABLES IN SCHEMA public FROM "<역할>";`(또는 `FROM PUBLIC;`. 열 단위 권한도 함께 거둠)으로 거두고, 예상하지 못한 트리거는 `DROP TRIGGER <이름> ON public.<테이블>;`로, 외래 키는 `ALTER TABLE <스키마>.<테이블> DROP CONSTRAINT <이름>;`으로 지웁니다. ⑥의 스키마는 그 안의 객체를 확인한 뒤 `DROP SCHEMA "<스키마>" CASCADE;`(다른 스키마에서 그 안의 객체를 쓰는 것도 함께 지움)나 `ALTER SCHEMA "<스키마>" OWNER TO "<마스터 사용자>";`(그 안 객체의 소유자는 바뀌지 않으므로 예상하지 못한 객체는 따로 지움)로 정리합니다. 새로 만든 PostgreSQL 15 이상 DB(예: RDS for PostgreSQL 16)는 필요 없습니다.
  ```sql
  SET search_path = pg_catalog;  -- 이 세션은 pg_catalog만 찾음 (public·"$user"에 심은 함수·연산자를 부르지 않음)
  WITH me AS (SELECT r.oid FROM pg_roles r WHERE r.rolname = current_user),
  x (classid, objid, nsp, owner) AS (
    SELECT 'pg_class'::regclass::oid, oid, relnamespace, relowner FROM pg_class WHERE relkind NOT IN ('i', 'I', 't', 'c')
    UNION ALL SELECT 'pg_proc'::regclass::oid, oid, pronamespace, proowner FROM pg_proc
    UNION ALL SELECT 'pg_type'::regclass::oid, t.oid, typnamespace, typowner FROM pg_type t WHERE NOT EXISTS (SELECT 1
      FROM pg_depend d WHERE d.classid = 'pg_type'::regclass::oid AND d.objid = t.oid AND d.deptype = 'i')
    UNION ALL SELECT 'pg_operator'::regclass::oid, oid, oprnamespace, oprowner FROM pg_operator
    UNION ALL SELECT 'pg_collation'::regclass::oid, oid, collnamespace, collowner FROM pg_collation
    UNION ALL SELECT 'pg_conversion'::regclass::oid, oid, connamespace, conowner FROM pg_conversion
    UNION ALL SELECT 'pg_opclass'::regclass::oid, oid, opcnamespace, opcowner FROM pg_opclass
    UNION ALL SELECT 'pg_opfamily'::regclass::oid, oid, opfnamespace, opfowner FROM pg_opfamily
    UNION ALL SELECT 'pg_ts_config'::regclass::oid, oid, cfgnamespace, cfgowner FROM pg_ts_config
    UNION ALL SELECT 'pg_ts_dict'::regclass::oid, oid, dictnamespace, dictowner FROM pg_ts_dict
    UNION ALL SELECT 'pg_statistic_ext'::regclass::oid, oid, stxnamespace, stxowner FROM pg_statistic_ext
    UNION ALL SELECT 'pg_extension'::regclass::oid, oid, extnamespace, extowner FROM pg_extension)
  -- ① public 스키마에서 마스터 사용자·부트스트랩 슈퍼유저(OID 10) 말고 다른 역할(기본 제공 역할 포함)이 소유한 객체
  SELECT i.type, i.identity, x.owner::regrole::text AS role
  FROM x, me, pg_identify_object(x.classid, x.objid, 0) i
  WHERE x.nsp = 'public'::regnamespace::oid AND x.owner <> me.oid AND x.owner <> 10::oid
  -- ② 마스터 사용자 이름의 스키마 (기본 search_path의 "$user"라 public보다 먼저 찾음)
  UNION ALL SELECT 'schema', n.nspname::text, n.nspowner::regrole::text FROM pg_namespace n WHERE n.nspname = current_user
  -- ③ public 테이블에 TRIGGER·REFERENCES 권한을 받은 역할 (vc_app·그 소속 역할·PUBLIC 등. REFERENCES는 열 단위 포함)
  UNION ALL SELECT a.privilege_type || ' privilege', c.oid::regclass::text || l.col,
    CASE WHEN a.grantee = 0::oid THEN 'PUBLIC' ELSE a.grantee::regrole::text END
  FROM pg_class c CROSS JOIN me
  CROSS JOIN LATERAL (SELECT ''::text, c.relacl UNION ALL SELECT ' (' || t.attname::text || ')', t.attacl
    FROM pg_attribute t WHERE t.attrelid = c.oid AND NOT t.attisdropped AND t.attacl IS NOT NULL) l (col, acl)
  CROSS JOIN LATERAL aclexplode(l.acl) a
  WHERE c.relnamespace = 'public'::regnamespace::oid AND a.privilege_type IN ('TRIGGER', 'REFERENCES')
    AND a.grantee <> me.oid
  -- ④ public 테이블의 트리거 (시스템 내부 트리거 제외. TRIGGER 권한을 거둬도 남음. WHEN 조건이 있으면 'trigger (WHEN)')
  UNION ALL SELECT CASE WHEN g.tgqual IS NULL THEN i.type ELSE i.type || ' (WHEN)' END,
    i.identity || ' -> ' || g.tgfoid::regprocedure::text, p.proowner::regrole::text
  FROM pg_trigger g, pg_class c, pg_proc p, pg_identify_object('pg_trigger'::regclass::oid, g.oid, 0) i
  WHERE c.oid = g.tgrelid AND p.oid = g.tgfoid AND c.relnamespace = 'public'::regnamespace::oid AND NOT g.tgisinternal
  -- ⑤ public 밖의 테이블에서 public 테이블을 참조하는 외래 키 (REFERENCES 권한을 거둬도 남음. 셋째 열은 그 테이블의 소유자)
  UNION ALL SELECT i.type, i.identity, c.relowner::regrole::text
  FROM pg_constraint k, pg_class p, pg_class c, pg_identify_object('pg_constraint'::regclass::oid, k.oid, 0) i
  WHERE k.contype = 'f' AND p.oid = k.confrelid AND c.oid = k.conrelid
    AND p.relnamespace = 'public'::regnamespace::oid AND c.relnamespace <> 'public'::regnamespace::oid
  -- ⑥ vc_app(이미 있으면)이나 vc_app이 속한 역할이 소유한 스키마 (마이그레이션이 거부)
  UNION ALL SELECT 'schema (vc_app)', n.nspname::text, n.nspowner::regrole::text
  FROM pg_namespace n, pg_roles r
  WHERE r.rolname = 'vc_app' AND pg_has_role(r.oid, n.nspowner, 'MEMBER'::text)
  ORDER BY 1, 2, 3;
  ```
- [ ] BE 서비스 계정을 한 번 만듭니다: 마스터 사용자로 `psql`에 접속해 `CREATE ROLE vc_app LOGIN;` 후 `\password vc_app`(비밀번호가 셸 기록·로그에 남지 않음). RDS는 퍼블릭 액세스 없이 두므로 `psql`은 CloudShell VPC 환경(`psql`이 미리 설치됨)이나 SSM Session Manager로만 접속하는 임시 EC2에서 실행하고, 끝나면 RDS 보안 그룹에 잠시 연 규칙을 지웁니다([deploy/README.md](README.md) ②). 슈퍼유저·`CREATEROLE`·`CREATEDB`·`rds_superuser` 같은 권한은 주지 않고, DB나 `public` 스키마의 소유자로 만들거나 CREATE 권한을 주지도 않으며, DB·`public` 스키마를 소유하거나 거기에 CREATE 권한이 있는 역할이나 슈퍼유저·`CREATEROLE`·`CREATEDB`·`REPLICATION`·`BYPASSRLS` 속성이 있는 역할의 소속으로 넣지도 않습니다(`NOINHERIT`·`GRANT ... WITH INHERIT FALSE` 소속도 마이그레이션이 거부). `vc_app`으로 `public` 스키마에 객체를 만들어 두지도 않습니다(`vc_app`이나 그 소속 역할, `pg_database_owner`·`pg_monitor` 같은 기본 제공 역할, `public`에 CREATE 권한이 있거나 DB·`public` 스키마를 소유한 다른 역할(마스터 사용자 제외)이 소유한 객체가 있으면 마이그레이션이 거부). 테이블에 `GRANT ALL`이나 `TRIGGER`·`REFERENCES` 권한, 원장 `schema_migrations`에 쓰기 권한도 주지 않습니다(`vc_app`이나 그 소속 역할, `PUBLIC`에 있으면 마이그레이션이 거부하고, 그 권한으로 만든 트리거·외래 키·원장 행은 권한을 거둔 뒤에도 남음. `vc_app` 자신에게 준 그 밖의 DML이 아닌 권한(`TRUNCATE` 등)은 마이그레이션이 실행할 때마다 거둠). `vc_app`이나 그 소속 역할이 소유한 스키마도 두지 않습니다(마이그레이션이 거부). 이 계정의 이름·비밀번호는 별도 Secrets Manager 비밀에 두고 BE 서비스 작업 정의의 `DB_USER`·`DB_PASSWORD`로 넣습니다.
- [ ] 마이그레이션은 서비스와 **다른 작업 정의**(같은 BE 이미지 태그, 템플릿 [deploy/ecs/be-migrate.taskdef.json](ecs/be-migrate.taskdef.json))로 실행합니다(`run-task` 덮어쓰기로는 `secrets`를 바꿀 수 없음): `DB_USER`·`DB_PASSWORD`는 마스터 사용자 비밀(DB와 테이블을 소유한 계정. 다른 관리 계정으로 실행하면 마스터 사용자가 소유한 테이블이 아래 소유 객체 검사에 걸림), `DB_APP_ROLE=vc_app`, `PGSSLMODE=verify-full`, 명령 `python -m app.migrate`(**`--seed`는 쓰지 않음**, `APP_ENV=production`이면 거부). 실행기는 끝날 때마다 `public` 테이블·시퀀스에서 `vc_app`의 권한을 모두 거둔 뒤 앱 테이블 SELECT·INSERT·UPDATE·DELETE와 시퀀스 사용 권한만 다시 줍니다(새 테이블 포함, 원장 `schema_migrations` 제외). `vc_app`이 없거나 특권 계정(마이그레이션 계정 자신이나 그 소속, 특권 속성이 있는 역할의 소속 포함)이거나, `vc_app`이나 `vc_app`이 속한 역할이 `public` 스키마·DB에 CREATE 권한이 있거나(`PUBLIC`에 준 CREATE 포함) DB·`public` 스키마나 그 밖의 스키마를 소유하거나 `public` 테이블에 `TRIGGER`·`REFERENCES`(열 단위 포함) 권한이나 원장 `schema_migrations`에 쓰기(`INSERT`·`UPDATE`·`DELETE`·`TRUNCATE`) 권한이 있거나(`PUBLIC`에 준 것 포함), 그 역할들이나 기본 제공 역할(`pg_database_owner`·`pg_monitor` 등), `public`에 CREATE 권한이 있거나 DB·`public` 스키마를 소유한 다른 역할(마스터 사용자 제외)이 `public` 스키마에 객체를 소유하거나, `public` 테이블의 트리거에 WHEN 조건이 있거나 그 트리거가 임시 스키마의 함수나 그 역할들이 소유한 함수를 부르면 종료 코드 1입니다. 이 검사는 마이그레이션 SQL을 하나라도 실행하기 전에 하고 권한을 주기 직전에 다시 하므로, 처음부터 걸리면 아무것도 적용하거나 주지 않습니다. 로그의 `마이그레이션 실패:` 줄이 걸린 검사·소속 역할 이름과 마스터 사용자로 나온 순서대로 실행할 GRANT·ALTER ... OWNER·REVOKE 문(예: `ALTER DATABASE "<DB 이름>" OWNER TO "<마스터 사용자>";`, `REVOKE CREATE ON DATABASE "<DB 이름>" FROM PUBLIC;`, `REVOKE TRIGGER ON ALL TABLES IN SCHEMA public FROM "vc_app";`, `REVOKE REFERENCES ON ALL TABLES IN SCHEMA public FROM "vc_app";`, `REVOKE ALL ON public.schema_migrations FROM "vc_app";`, `DROP SCHEMA "<스키마>" CASCADE; 또는 ALTER SCHEMA "<스키마>" OWNER TO "<마스터 사용자>";`)이나 소유한 객체·스키마·트리거·외래 키 목록(`TRIGGER` 권한으로 걸리면 그 권한으로 만든 트리거가 REVOKE 뒤에도 남으므로 `public` 테이블의 트리거도, `REFERENCES` 권한으로 걸리면 같은 이유로 `public` 밖 테이블에서 `public` 테이블을 참조하는 외래 키도)을 알려 줍니다. 원장 쓰기 권한으로 걸리면 그 권한으로 넣거나 바꾼 원장 행이 남으므로 원장이 실제로 적용한 마이그레이션과 맞는지 확인합니다. 마스터 사용자 비밀은 이 작업 정의에만 연결합니다.
  - 슈퍼유저가 아닌 마스터 사용자는 다른 역할이 소유한 DB·스키마(`public`, `vc_app`이 소유한 스키마 등)의 소유자를 바로 바꾸거나 그 스키마를 지우지 못합니다(`must be owner of database ...`·`must be owner of schema ...`). 그래서 마이그레이션 계정이 슈퍼유저가 아니면 로그 줄이 ALTER ... OWNER·DROP SCHEMA 문보다 먼저 `GRANT "<소유한 역할>" TO "<마스터 사용자>" WITH INHERIT TRUE;`(PostgreSQL 16 기준)를 알려 줍니다. 마스터 사용자가 만든 역할(`vc_app` 등)이 소유자면 마스터 사용자에게 그 역할의 ADMIN 권한이 있어 그대로 실행할 수 있고, 로그의 문을 나온 순서대로 다 실행한 뒤 `REVOKE "<소유한 역할>" FROM "<마스터 사용자>";`로 그 소속을 다시 거둡니다(이 REVOKE는 로그에 나오지 않음. 그 역할을 만들 때 받은 ADMIN 권한은 그대로 남음).
  - 소유자를 바꿀 때 지금 소유자 몫의 CREATE를 이미 거둔 상태면 로그 줄이 ALTER 문 뒤에 새 소유자에게 CREATE를 다시 주는 문도 알려 줍니다: `GRANT CREATE ON SCHEMA public TO pg_database_owner;`(PostgreSQL 14 이하는 `TO "<마스터 사용자>"`), `public` 스키마의 소유자도 함께 바꿀 때는 `GRANT CREATE ON DATABASE "<DB 이름>" TO "<마스터 사용자>";`. 로그 없이 직접 예전 소유자의 CREATE를 먼저 거둔 뒤 소유자를 바꿨다면 새 소유자도 CREATE가 없어 마이그레이션이 `permission denied for schema public`으로 실패하므로, 마스터 사용자로 같은 GRANT 문을 실행한 뒤 다시 실행합니다.

## FE

- [ ] Node.js 22.12 이상에서 `cd FE && npm ci && npm run build` 후 `dist/`를 S3(비공개, CloudFront OAC)에 올립니다. `VITE_API_BASE_URL`은 빌드 때 번들에 들어갑니다: 비우면 `/api`(같은 출처에서 CloudFront 동작 `/api/*` → BE용 ALB), API가 다른 도메인이면 `/api`까지 넣은 `https://api.example.com/api`. FE는 CloudFront 주소를 몰라도 되므로 배포판보다 먼저 빌드해도 됩니다.
- [ ] 올리는 순서와 캐시: 해시가 붙은 `assets/`를 먼저 `Cache-Control: public,max-age=31536000,immutable`로(`--delete` 없이, 이전 자산은 한 번 더 배포한 뒤에 지움), `index.html`을 마지막에 `Cache-Control: no-cache`·`Content-Type: text/html; charset=utf-8`로 올리고 `/index.html`을 무효화합니다. 순서가 바뀌거나 이전 자산을 먼저 지우면 빈 화면이 됩니다. JS·CSS가 `text/javascript`·`text/css`로 올라갔는지, 기본 동작의 캐시 정책(`Managed-CachingOptimized`)으로 `br`·`gzip` 압축이 되는지도 봅니다(명령은 [deploy/README.md](README.md) ⑨).
- [ ] `/api/*` 동작은 캐시하지 않고(`Managed-CachingDisabled`), `Authorization` 헤더를 넘기고(`Managed-AllViewerExceptHostHeader`), 모든 HTTP 메서드를 허용합니다.
- [ ] SPA history fallback: `/dashboard` 같은 경로를 새로고침해도 `/index.html`(200)을 돌려주게 합니다. CloudFront 오류 페이지(403/404 → `/index.html`)는 배포 전체에 적용되므로 API가 다른 도메인일 때만 씁니다. `/api/*`가 같은 배포에 있으면 BE의 403/404 JSON까지 바뀌어 화면의 오류 처리가 깨지므로, 기본(S3) 동작에만 CloudFront Function으로 처리합니다([FE/README.md](../FE/README.md) "운영 빌드"). 함수는 [deploy/cloudfront/spa-fallback.js](cloudfront/spa-fallback.js)(런타임 `cloudfront-js-2.0`, 뷰어 요청)를 그대로 씁니다: `/api/`로 시작하거나 마지막 경로 조각에 점이 있는 요청(자산)은 그대로 두고, 그 밖은 쿼리를 남긴 채 `/index.html`로 바꿉니다(`node deploy/cloudfront/spa-fallback.test.cjs`로 확인). 이 함수가 없으면 소셜 로그인 콜백(`/auth/<제공자>/callback`)과 공유 링크(`/share/<token>`)의 첫 방문도 403이 되고, AWS 문서의 SPA 예시 함수(`/dashboard` → `/dashboard/index.html`)도 이 앱에서는 403이므로 쓰지 않습니다.
- [ ] 보안 응답 헤더: CloudFront 응답 헤더 정책(사용자 지정)을 하나 만들어 기본(S3) 동작에 연결합니다(`/api/*`에 함께 연결해도 됨). 헤더마다 원본 재정의(Origin override)를 켭니다.
  - `Strict-Transport-Security: max-age=31536000` (모든 하위 도메인이 HTTPS일 때만 `includeSubDomains`, `preload`는 쓰지 않음)
  - `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` (`X-XSS-Protection`은 넣지 않음)
  - `Content-Security-Policy`(한 줄): `default-src 'self'; script-src 'self'; style-src 'self' https://cdn.jsdelivr.net; font-src 'self' data: https://cdn.jsdelivr.net; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`
  - Pretendard 웹폰트는 아직 jsDelivr CDN에서 받으므로(`FE/src/main.tsx`가 스크립트로 붙이는 스타일시트 `<link>`. `index.html`에는 없어 CDN이 느려도 첫 화면을 막지 않음. 자체 호스팅은 [FE/README.md](../FE/README.md) TODO) `style-src`·`font-src`에서 `https://cdn.jsdelivr.net`을 빼면 글꼴이 시스템 글꼴로 바뀝니다. API를 다른 도메인에 두면 `connect-src`에 그 출처를 더합니다(예: `connect-src 'self' https://api.example.com`). FE가 다른 출처의 리소스를 새로 쓰면 이 값도 함께 바꿉니다.
  - 처음에는 같은 값을 사용자 지정 헤더 `Content-Security-Policy-Report-Only`로 넣고 아래 "배포 후 확인"을 한 번 한 뒤(콘솔에 CSP 경고가 없으면) `Content-Security-Policy`로 바꿔도 됩니다.

## HTTPS·네트워크

- [ ] FE와 API 모두 브라우저에는 HTTPS로만 서비스합니다. HTTPS 페이지는 `http://` API를 부를 수 없고, 평문 HTTP면 비밀번호·토큰이 그대로 오갑니다. 도메인 없는 기본 구성은 브라우저 쪽 HTTPS를 CloudFront 기본 인증서(`*.cloudfront.net`)가 맡고, CloudFront → BE 구간은 CloudFront **VPC 원본**으로 내부 ALB의 HTTP:80에 비공개로 연결합니다(ALB에 붙일 ACM 공인 인증서는 자기 도메인이 있어야 발급되므로). 자기 도메인을 붙이면 아래 "자기 도메인" 설정으로 올립니다.
  - CloudFront의 모든 동작(기본 S3, `/api/*`)에서 뷰어 프로토콜 정책을 `Redirect HTTP to HTTPS`로 둡니다(콘솔 기본값 `HTTP and HTTPS`는 평문 요청도 받음). 기본 인증서(`*.cloudfront.net`)를 쓰면 CloudFront가 보안 정책을 `TLSv1`로 정하고 바꿀 수 없습니다(요즘 브라우저는 TLS 1.2 이상으로 접속하므로 받아들임). 자기 도메인: us-east-1의 ACM 인증서를 붙이고 최소 보안 정책을 `TLSv1.2_2021` 이상으로.
  - CloudFront → BE용 ALB 원본: 기본 구성은 VPC 원본(내부 ALB)이고, 프로토콜 `HTTP only`·HTTP 포트 80은 배포판의 원본이 아니라 **VPC 원본 자원**에서 정합니다(`Match viewer`·`HTTPS only`면 ALB 443에 리스너가 없어 모든 `/api/*`가 502. 배포판 쪽 원본 설정은 응답 제한 시간·keep-alive·연결 시도뿐). 이 구간은 CloudFront와 VPC 사이의 비공개 연결이고 ALB는 인터넷에 열리지 않습니다. 자기 도메인: `HTTPS only`(ALB 443 리스너에 원본 도메인 이름의 ACM 인증서). **공개 ALB를 `HTTP only` 원본으로 쓰지 않습니다**(인터넷 구간에서 비밀번호·토큰·`X-Origin-Verify` 값이 평문으로 오감).
  - 기본 구성의 내부 ALB는 HTTP:80 리스너 하나만 BE 대상 그룹(대상 유형 `ip`, 3000)으로 보내고 80 → 443 리디렉션은 넣지 않습니다(CloudFront는 원본의 리디렉션을 따라가지 않음). 자기 도메인: ALB는 443 리스너만 대상 그룹으로 보내고 80 리스너는 두지 않거나 기본 동작을 `HTTPS:443` 리디렉션(301)으로만 둡니다. 어느 쪽이든 S3 정적 웹 사이트 호스팅(HTTP 전용 엔드포인트)은 켜지 않습니다(CloudFront OAC로만 읽음).
  - API를 다른 도메인(ALB 직접)으로 서비스하면 CloudFront 응답 헤더 정책이 API 응답에는 붙지 않습니다. BE가 모든 응답에 `Cache-Control: no-store`·`X-Content-Type-Options`·`X-Frame-Options`·`Content-Security-Policy: frame-ancestors 'none'`·`Referrer-Policy`를, `APP_ENV=production`에서는 `Strict-Transport-Security`도 직접 붙이므로 ALB에는 80 → 443 리디렉션만 둡니다.
- [ ] BE용 ALB는 CloudFront를 거친 요청만 받게 합니다. 아니면 ALB 주소로 바로 보내 아래 WAF 규칙을 건너뜁니다. 기본 구성: ALB를 내부(internal, 프라이빗 서브넷 2개)로 만들고 CloudFront **VPC 원본**으로 연결한 뒤, ALB 보안 그룹 인바운드 80을 VPC 원본이 만든 `CloudFront-VPCOrigins-Service-SG`에서만 허용합니다(VPC 원본을 만든 뒤에 추가. VPC에는 인터넷 게이트웨이가 붙어 있어야 VPC 원본을 만들 수 있음). 자기 도메인으로 공개 ALB(HTTPS 원본)를 쓰는 경우에만: ① ALB 보안 그룹 인바운드 443을 AWS 관리형 접두사 목록 `com.amazonaws.global.cloudfront.origin-facing`에서만 허용하고(보안 그룹 규칙 할당량을 많이 차지하므로 이것만 두는 전용 보안 그룹), ② CloudFront 원본에 사용자 지정 헤더(예: `X-Origin-Verify`, 값은 Secrets Manager의 긴 무작위 값)를 넣고 ALB 리스너 규칙은 그 헤더가 맞을 때만 BE 대상 그룹으로 보내며 기본 동작은 고정 응답 403으로 둡니다(접두사 목록에는 다른 사람의 CloudFront 배포도 들어 있으므로 ②까지 필요). - [ ] 요청 본문 크기: BE가 경로별 상한(`BE/main.py`의 `body_limit`)을 넘는 본문을 413으로 끊으므로(`Content-Length`로 알리면 읽기 전에, chunked 전송이면 상한 남짓까지만 읽고) 설정할 값은 없습니다(ALB는 본문 크기를 제한하지 않음). 상한은 기본 64 KiB, 토큰 없이 부르는 `POST /api/v1/users/login`·`POST /api/v1/users/register`·`POST /api/v1/users/oauth/{google,github,naver}/callback` 16 KiB, `POST /api/v1/verify` 320 KiB, 연구자용 `POST /api/v1/research/*` 세 경로 2 MiB입니다. WAF·프록시에 본문 크기 규칙을 더한다면 `/api/v1/research/*`(공고 반입 최대 약 1.75 MiB)와 `/api/v1/verify`(VC-JWT 최대 256 KiB)를 막지 않게 합니다. 연구자용 세 경로는 본문 형식 검사보다 먼저 연구자인지 확인하므로, 연구자가 아닌 계정이 보낸 큰 본문은 형식 검사 없이 403입니다(본문을 읽고 JSON으로 푸는 것까지는 함). 필요하면 이 경로에도 IP별 속도 규칙을 둡니다(예: `POST` + URI 경로가 `/api/v1/research/`로 시작, 100회. 연구자의 반입 작업량에 맞춰 조정).
- [ ] BE는 DXWorks·AI·소셜 로그인 제공자 호출에 `HTTP_PROXY`·`HTTPS_PROXY`·`ALL_PROXY` 같은 프록시 환경변수를 쓰지 않고 리디렉션도 따라가지 않습니다. 프라이빗 서브넷의 BE는 NAT 게이트웨이 같은 VPC 라우팅으로 DXWorks와, 켠 소셜 로그인 제공자의 HTTPS(443) 호스트에 나갑니다: Google `oauth2.googleapis.com`·`openidconnect.googleapis.com`, GitHub `github.com`(토큰)·`api.github.com`(사용자 정보·이메일 목록), 네이버 `nid.naver.com`(토큰)·`openapi.naver.com`(사용자 정보). 인가 화면(`accounts.google.com`·`github.com`·`nid.naver.com`)은 사용자 브라우저가 엽니다. 나가는 주소를 막는 방화벽을 둔다면 이 호스트를 허용합니다. 그와 별도로 모든 태스크(BE·AI·마이그레이션)는 시작할 때 ECR(이미지 층은 S3)·Secrets Manager·CloudWatch Logs에 닿아야 하므로, 프라이빗 서브넷 + NAT 게이트웨이(나가는 IP가 하나로 고정되어 DXWorks IP 허용 목록에 맞음) 또는 퍼블릭 서브넷 + 태스크 공인 IP(NAT 비용 없음, IP가 태스크마다 바뀜) 중 하나를 고르고, 필요하면 VPC 엔드포인트를 더합니다(비용 비교와 표는 [deploy/README.md](README.md) ①). AI는 LLM 모드를 켰을 때만 `CURRICULUM_LLM_BASE_URL` 호스트로 나갑니다.
- [ ] ALB 뒤에서는 작업 정의에 `FORWARDED_ALLOW_IPS`(VPC CIDR, 예: `10.0.0.0/16`, CIDR 표기 가능)를 넣어 uvicorn이 ALB의 `X-Forwarded-*` 헤더를 믿게 합니다(uvicorn 0.54.0 기본값은 `127.0.0.1,::1`, 프록시 헤더 처리는 기본으로 켜져 있음). 지금 BE는 클라이언트 IP를 쓰지 않으므로(로그인 실패 제한도 IP가 아니라 이메일별) 접근 로그에만 영향이 있습니다. CloudFront를 거치면 접근 로그의 IP는 보통 사용자 IP가 아니라 CloudFront 엣지 주소이므로, 사용자 IP는 CloudFront·WAF 로그로 봅니다. 기본 구성의 VPC 원본·HTTP:80 원본 뒤에서는 `X-Forwarded-Proto`가 `http`이지만 BE는 요청의 스킴·`Host`로 주소를 만들지 않으므로(HSTS도 `APP_ENV`로만 정함) 영향이 없습니다.
- [ ] 시간 제한: LLM 커리큘럼은 BE가 AI를 최대 90초(`AI_GENERATION_TIMEOUT_SECONDS`) 기다리고 FE는 120초까지 기다립니다. DXWorks 호출 한 번은 최악의 경우 `DXWORKS_TIMEOUT_SECONDS`의 4배(기본 60초)입니다.
  - CloudFront `/api/*` 원본(VPC 원본)의 **응답 제한 시간을 120초**로 둡니다(기본 30초. 할당량 범위가 1–120초라 요청 없이 설정됨. LLM 모드를 끄고 쓰면 최소 65초). 30초 그대로면 CloudFront가 먼저 504를 돌려줘 FE는 "서버에 연결할 수 없습니다"를 보여 주는데, BE는 요청을 끝까지 처리하므로(모의 발급·LLM 커리큘럼은 성공했을 수 있음) 사용자가 다시 시도하면 일과 협력사 호출이 겹칩니다.
  - 같은 원본의 **연결 시도는 1회**(기본 3회)로 둡니다. GET·HEAD는 응답 제한 시간 안에 답이 없으면 연결 시도 수만큼 다시 보내므로 DXWorks를 부르는 `GET /api/v1/public/shares/{token}`·`GET /api/v1/subjects/{did}/evidence`가 되풀이될 수 있습니다(POST는 다시 보내지 않음).
  - ALB 유휴 제한 시간을 120초 이상(기본 60초)으로 올리고, uvicorn keep-alive(기본 5초)는 ALB 유휴 제한보다 길게 둡니다(예: ALB 120초면 `UVICORN_TIMEOUT_KEEP_ALIVE=130`).
  - AI를 ECS Service Connect로 연결하고 포트 매핑 `appProtocol`을 HTTP로 두면 요청별 제한 시간(`perRequestTimeoutSeconds`) 기본값이 15초라 LLM 커리큘럼 호출이 끊기므로(503 "AI service temporarily unavailable"), AI 서비스의 Service Connect 설정에서 120초로 올립니다.
  - 배포·축소 때 처리 중인 요청이 잘리지 않게 BE 대상 그룹의 등록 취소 지연(`deregistration_delay.timeout_seconds`, 기본 300초)을 CloudFront 응답 제한 시간(120초)보다 긴 130초로, BE·AI 컨테이너의 `stopTimeout`을 120초(Fargate 최대, 기본 30초)로 둡니다. ECS는 먼저 대상을 등록 취소하고 그 지연 동안 진행 중인 요청이 끝나기를 기다린 뒤 SIGTERM을 보내며(그래서 배포·축소마다 옛 태스크가 약 2분 더 남음), `stopTimeout`은 그 뒤 SIGKILL까지의 여유입니다(uvicorn은 종료 신호를 받으면 처리 중인 요청을 마치고 끝남. ALB가 없는 AI는 이 값이 진행 중인 LLM 요청을 지킴).

- [ ] `/health`(인증 없음, DB는 확인하지 않음): BE 3000번, AI 8100번. BE의 `/health`는 워커 스레드를 쓰지 않고 이벤트 루프에서 바로 답하므로, DB 연결 자리나 잠금을 기다리는 요청이 워커 스레드를 모두 잡고 있어도(각 최대 5초) 상태 확인이 함께 밀리지 않습니다. Exiting.`을 남기고 종료 코드 3으로 끝나 배포 회로 차단기가 롤백합니다. 그래서 작업 정의 `healthCheck`의 `startPeriod`는 60초, ALB 상태 확인 유예는 90초쯤으로 둡니다. 요약별 원인은 [deploy/README.md](README.md) "문제 해결". - [ ] 작업 크기·하드닝: BE 태스크는 1 vCPU·2 GB(앱 몫 최소 0.5 vCPU·1 GB + Service Connect 프록시 256 CPU·64 MiB. 0.25 vCPU에서는 bcrypt 로그인 한 번이 약 1.7초라 한 IP가 WAF 한도 안에서 로그인을 줄 세울 수 있음), AI는 0.5 vCPU·1 GB, 마이그레이션은 0.25 vCPU·0.5 GB로 시작하고 실제 Fargate에서 다시 잽니다. 세 컨테이너 모두 `readonlyRootFilesystem: true`로 동작합니다(쓰기 가능한 마운트가 필요한 것은 `python -m app.jobs.market export`뿐). 템플릿은 [deploy/ecs](ecs).
- [ ] 로그는 stdout(`PYTHONUNBUFFERED=1`)으로 나오므로 `awslogs` 로그 드라이버로 CloudWatch Logs에 보냅니다. 로그 그룹(`/ecs/vc-be`·`/ecs/vc-ai`)은 첫 태스크보다 먼저 만들고(작업 정의는 `awslogs-create-group`을 쓰지 않으므로 그룹이 없으면 태스크가 `ResourceInitializationError`로 시작하지 못함, [deploy/README.md](README.md) ①) 보존 기간을 정합니다(기본값은 만료 없음, 예: 30~90일). BE는 `LOG_LEVEL`로 수준을 정합니다. 지표 필터 예: `AI service error`, `Credential re-verification failed`, `Provider error`, `Public share view rejected`, `Database busy`, `Mock issuance outcome unknown`, `Market snapshot integrity check failed`, `Google OAuth token request rejected`·`GitHub OAuth token request rejected`·`Naver OAuth token request rejected`, `Rejected unstorable text`(경고), `Unhandled error`(오류), 시작 실패를 잡는 `DB startup check failed`·`APP_ENV=production requires`·`마이그레이션 실패`. 협력사 오류 코드·메시지와 빠진 설정 이름은 응답에 싣지 않고 `Provider error` 줄(한 줄, 300자까지)에만 남습니다.
- [ ] 감사 로그: 로거 `vc-be.audit`가 INFO로 한 줄씩 남깁니다(같은 stdout, 줄 머리 `INFO:vc-be.audit:`. 이메일·DID·토큰·이름은 싣지 않음). `LOG_LEVEL`을 `WARNING` 이상으로 올리면 남지 않습니다.
  - `event=verifier_calls user=<사용자 UUID|service|anonymous> route=<verify_badge|verify_identity|reverify|evidence|portfolio_create|career_analysis|share_view> calls=<부른 수> failed=<그중 실패 수>`: DXWorks 검증기를 부른 요청마다.
  - `event=verifier_budget_denied user=<사용자 UUID|service> route=<…> retry_after=<초>`: 호출 한도로 429를 돌려준 요청마다. 토큰이 거절된 배지 검증이 10분에 10번을 넘어 막힌 요청은 `route=verify_rejected`.
  - `event=verify_shape_refused user=<사용자 UUID>`: `POST /api/v1/verify`의 배지 토큰이 JWT 모양 검사에 걸려 DXWorks로 보내지 않은 요청마다(이때는 `verifier_calls` 줄이 없음).
  - `event=login_locked key=<이메일 SHA-256의 앞 12자리> retry_after=<초>`: 로그인 실패 제한으로 잠긴 이메일에 온 시도마다.
  - `event=oauth_login outcome=<created|linked|login|refused_password_account|refused_unverified_link> user=<사용자 UUID> provider=<google|github|naver>`: 소셜 로그인 결과마다(두 `refused_*`의 `user`는 그 로그인을 붙이지 않은 기존 계정: 비밀번호 계정, 또는 이메일이 양쪽에서 확인되지 않은 계정. 끝의 `provider=`는 Google 줄에도 붙으므로 예전 Google 줄 전체와 같아야 하는 필터는 고침).
  - `event=oauth_exchange_denied retry_after=<초> provider=<google|github|naver>`: 그 제공자의 토큰 교환 한도(태스크마다 제공자별 분당 300번)로 429를 돌려준 콜백마다.
  - `event=corpus_budget_denied user=<사용자 UUID> route=</v1/job-postings/search|/v1/learning-resources/search|/v1/career-analyses|/v1/curricula/context> reason=<in_flight|rate> retry_after=<초>`: 사용자별 AI 묶음 요청 한도(동시 2개·분당 30번·시간당 300번)로 429를 돌려준 요청마다.
  - `event=daily_limit_denied user=<사용자 UUID> route=<career_analysis|curriculum|curriculum_llm> retry_after=<초>`: 사용자별 24시간 한도(직무 비교 200건, 학습 계획 200건, LLM 학습 계획 `CURRICULUM_LLM_DAILY_LIMIT`건)로 429를 돌려준 요청마다.
  - `event=llm_service_limit_denied user=<사용자 UUID> retry_after=<초>`: 모든 계정을 합친 24시간 LLM 학습 계획 한도(`CURRICULUM_LLM_GLOBAL_DAILY_LIMIT`, 기본 200)로 429를 돌려준 요청마다. `CURRICULUM_LLM_USER_IDS=*`로 연 뒤 자주 보이면 가입 남용이나 한도 조정을 확인합니다.
  - `event=llm_in_flight_denied user=<사용자 UUID>`: 같은 계정의 LLM 모드 학습 계획이 이미 진행 중이라 429를 돌려준 요청마다(계정당 동시 1건).
  - CloudWatch Logs 지표 필터 패턴 예(등호가 든 말은 큰따옴표로 감쌈): `"event=verifier_budget_denied"`(검증기 호출 한도에 닿음. 계속 나오면 한 계정·IP가 몰아 보내는지 `user`로 확인), `"event=login_locked"`(잠긴 이메일에 대한 시도), `"event=oauth_login" "outcome=refused_password_account"`(같은 `user`에 반복되면 그 주소를 남이 먼저 가입해 둔 것일 수 있음), `"event=oauth_exchange_denied"`(그 `provider`의 소셜 로그인이 모든 사용자에게 429가 되고 있음. WAF의 콜백 규칙과 차단 지표를 확인), `"event=verify_shape_refused"`(발급한 배지의 검증에서 나오면 토큰 형식이 모양 검사와 맞지 않는 것. 아래 "배포 후 확인"). `verifier_calls` 줄의 `calls`를 분 단위로 더한 값이 그 태스크가 DXWorks로 보낸 검증 호출 수이고, 로그인 사용자 몫의 태스크 한도는 분당 600입니다.
- [ ] BE 접근 로그는 공유 링크 토큰과 DID를 가리고(`/api/v1/public/shares/[redacted]`, `/api/v1/subjects/[did]/...`), 소셜 로그인 콜백 경로(`…/google/callback?…`·`…/github/callback?…`·`…/naver/callback?…`)의 쿼리를 통째로 가립니다(`?[redacted]`). 공유 링크 토큰은 아직 URL 경로에 들어가므로(경로에서 빼는 변경은 하지 않음) CloudFront·ALB 접근 로그를 켜면 그 로그에는 토큰이 그대로 남습니다. 제공자가 FE 콜백 주소(`https://<FE 도메인>/auth/<제공자>/callback?code=…&state=…`)로 돌려보내는 요청의 쿼리(한 번만 쓸 수 있는 인가 코드와 `state`)도 CloudFront 접근 로그에는 남습니다(FE는 콜백 화면에서 주소창의 쿼리를 바로 지우고 `POST` 본문으로 BE에 보냄). 켠다면 로그 버킷 접근을 좁히고 보존 기간을 짧게 둡니다. 특히 네이버는 PKCE를 쓰지 않아, 사용자의 `POST`가 끝나지 않은 콜백 주소(탭을 닫았거나 네트워크 오류)를 로그에서 본 사람이 코드가 만료되기 전에 그 `code`·`state`로 대신 로그인할 수 있습니다. CloudFront 로그를 켜면 `/auth/*/callback`의 쿼리 문자열은 남기지 않게(실시간 로그는 필드 선택, 표준 로그는 버킷 접근 최소화) 둡니다.

  - 발급한 배지의 검증: 스테이징에서 배지를 하나 발급해 `POST /api/v1/verify`로 보냅니다(`MOCK_ISSUER_ENABLED=true`면 발급 화면에서 "검증하고 지갑에 저장하기"까지. 모의 발급을 켜지 않는 배포면 협력사가 실제로 발급한 배지 토큰을 API로 직접 보냄). `success: true`로 저장되고 BE 로그에 `event=verifier_calls … route=verify_badge calls=1 failed=0` 줄이 남으면 됩니다. 응답이 200 `success: false`·`Badge verification failed.`(화면은 "배지 검증에 실패했습니다")인데 로그에 `event=verify_shape_refused` 줄이 있고 `event=verifier_calls` 줄이 없으면, 실제 토큰의 형식이 BE의 JWT 모양 검사(compact JWS, 조각 끝의 `=` 패딩, SD-JWT만 받음)와 맞지 않아 DXWorks로 보내지도 않은 것입니다. 위조 배지를 거절할 때와 같은 응답이라 화면만으로는 구분되지 않고, 이 상태에서는 발급한 배지를 지갑에 넣을 수 없으므로 서비스를 열기 전에 팀에 알립니다(`BE/app/domain/credential.py`의 `is_compact_jws`를 실제 형식에 맞춰야 함).
  - 압축 응답: 배지 검증이나 모의 발급이 502이고 BE 로그의 `Provider error:` 줄이 `DXWorks가 요청하지 않은 압축 응답을 반환했습니다`면, 협력사(또는 중간 CDN)가 BE의 `Accept-Encoding: identity` 요청과 달리 `gzip`·`deflate`가 아닌 방식(`br`·`zstd`, 겹친 압축 등)으로 압축한 응답을 보낸 것입니다. `gzip`·`deflate` 응답은 BE가 1 MiB 상한 안에서 직접 풀지만 그 밖의 방식은 거절하므로, 이 줄이 나오면 모든 DXWorks 호출이 실패합니다(코드 수정이 필요하니 팀에 알림).
  - 쓰레기 토큰에 대한 협력사 응답: 스테이징에서 JWS 모양만 맞춘 쓰레기 토큰 하나를 `POST /api/v1/verify`로 보내고(`{"type": "badge", "token": "eyJhbGciOiJFZERTQSJ9.e30.AAAA"}`) 협력사가 무엇으로 답했는지 적어 둡니다.   - 공개 항목이 덧붙은 배지: 위에서 발급한 실제 배지 토큰 끝에 쓰레기 공개 항목 하나를 붙여(`<jws>~AAAA~`) 같은 API로 보내고 협력사가 받아들이는지 적어 둡니다. BE의 모양 검사는 SD-JWT 형식을 받으므로 이 토큰은 DXWorks까지 가고, 협력사가 덧붙은 부분을 무시하고 통과시키면(`success: true`) 그 문자열 그대로 서명 원본으로 저장되어 공유 링크 조회에도 나갑니다.

## 하지 않은 것 (운영 전에 알아 둘 것)

- DXWorks 응답: `valid: true`만 있고 서명·발급자 신뢰 결과가 빠진 2xx 응답도 지금은 통과(`verified`)로 처리합니다. 두 항목이 반드시 있어야 통과시키는 검사는 실제 응답 표본을 확인한 뒤로 미뤘습니다. (`valid`가 참·거짓이 아닌 응답은 판정으로 읽지 않고 검증기 오류로 처리합니다.) 실제 DXWorks가 발급한 토큰이 BE의 JWT 모양 검사를 통과하는지, 실제 서버가 어떤 압축으로 응답하는지도 실제 서버로는 확인하지 못했습니다(위 "배포 후 확인"의 DXWorks 첫 연결 확인).
- DXWorks 호출: 호출마다 새 연결을 엽니다. 요청한 쪽이 연결을 끊어도 이미 시작한 재검증은 끝까지 돕니다(호출 수는 위 한도로 묶임). 근거 조회 API(`GET /api/v1/subjects/{did}/evidence`)와 서비스 키(`SERVICE_API_KEY`)는 그대로 있습니다.
- 한도의 범위: BE 자체 한도는 태스크마다 따로 세고 재시작하면 지워집니다(IP별 제한은 WAF). 직무 비교·학습 계획은 사용자별로 24시간에 각 200건(DB로 셈), LLM 모드 학습 계획은 `CURRICULUM_LLM_DAILY_LIMIT`건(기본 20)까지이고, 지난 직무 비교·학습 계획을 지우는 정리 작업은 없습니다(계정 하나가 쌓는 양은 하루 약 400건으로 묶임). 검증기 호출에는 하루 단위 한도가 없고 가입 수도 제한하지 않으므로, 계정을 30개쯤 만들어 계속 부르면 태스크의 검증기 몫(분당 600번)을 비워 둘 수 있고 그동안 다른 사용자의 검증·재검증·포트폴리오 저장·직무 비교는 429입니다(그때도 로그인 사용자 몫으로 DXWorks에 나가는 호출은 태스크마다 분당 600번 수준으로 묶임). 소셜 로그인 토큰 교환 몫(제공자별 분당 300번)도 여러 IP에서 몰아 보내면 비울 수 있습니다. 둘 다 WAF의 IP별 규칙과 감사 로그 지표(`event=verifier_budget_denied`·`event=oauth_exchange_denied`)로 보고 대응합니다.
- 배지 검증의 거절 창: 검증기 장애로 보는 답(5xx·401·403·408·429·3xx, 응답 없음)은 창에 세지 않습니다(실제 장애 때 사용자가 잠기지 않게). 그래서 실제 DXWorks가 쓰레기 토큰에 4xx가 아니라 5xx로 답한다면, 쓰레기 토큰은 10분에 10번이 아니라 계정별 호출 몫(첫 한 시간 2,400번쯤, 그 뒤 분당 20번)만큼 DXWorks로 나갑니다. 장애로 끝난 검증을 따로 세는 창은 두지 않았습니다(위 "배포 후 확인"에서 실제 응답을 확인). 신원 VP 검증(`type: identity`, 기본으로 꺼져 있음)에는 거절 창이 없어, 켜면 계정별 호출 몫만 적용됩니다.
- 일괄 재검증: DXWorks가 장애 응답(5xx 등) 없이 모든 호출에 판정이 아닌 200이나 400으로 답하는 상태에서는 재검증 한 건이 502가 아니라 200 `success: false`(`verifier_error`)입니다. 그래서 FE의 일괄 재검증이 첫 항목에서 멈추지 않고 자격증명마다 한 번씩 부릅니다(계정별 호출 몫 안이고 저장된 상태는 바뀌지 않음. 화면에는 모든 항목이 "검증 서버가 확인하지 못함"으로 나옴).
- 공유 링크 조회의 대기: 같은 서명 원본을 먼저 물은 조회를 기다리는 시간은 조회 전체가 아니라 자격증명마다 `DXWORKS_TIMEOUT_SECONDS`의 4배까지입니다. 자격증명은 5개씩 처리하므로, 먼저 물은 호출이 끝내 끝나지 않으면(어댑터의 시간 제한까지 듣지 않는 고장이 겹친 경우) 조회 하나가 (자격증명 수 ÷ 5, 올림) × 4배만큼 걸릴 수 있습니다(50개, 기본 15초면 10분). 한 번 기다림이 시간 초과로 끝난 뒤 남은 자격증명의 기다림을 건너뛰는 처리는 하지 않았습니다.
- 모의 발급의 실패 차단기: 발급을 멈춘 동안 1분에 한 건 나가는 요청은 그때 먼저 온 요청이므로 어느 계정이든 차지할 수 있습니다(DB 한도나 설정 누락으로 협력사에 가지 못한 요청은 그 기회를 쓰지 않음). 그 한 건만 성공하고 나머지는 실패하는 협력사(예: 우리를 분당 한 건쯤으로 제한)나, 허용 템플릿 가운데 발급되는 것과 협력사가 거절하는 것을 번갈아 보내는 계정들 앞에서는 성공할 때마다 실패 기록이 지워져 다시 `MOCK_ISSUER_GLOBAL_DAILY_LIMIT`번까지 나가므로, 그때 실패한 발급 요청의 하루 양은 차단기가 아니라 계정 수 × 사용자별 시도 한도(기본 하루 30번)가 묶습니다(해시까지 기록된 성공한 발급은 DB 발급 한도가 그대로 묶고, 해시를 기록하지 못한 발급은 진행 중 창 10분이 지나면 사용자별 하루 발급 한도 × 계정 수만 묶음).
- 관리형 지갑(홀더 키): 가입할 때 사용자마다 홀더 개인키를 만들어 암호화해 `holder_keys`에 저장하지만, 그 키를 복호화하거나 그 키로 서명하는 코드(`BE/app/services/key_custody.py`의 `sign`)를 부르는 곳은 아직 없습니다(신원 자격증명 기능용으로 남겨 둔 것). 그래서 `HOLDER_KEY_ENCRYPTION_KEY`가 바뀌어 기존 키를 복호화할 수 없게 되어도 BE는 알아채지 못하고 `GET /api/v1/users/me`는 계속 `wallet.custody: managed`로 답합니다. 시작할 때 마스터 키를 확인하는 검사와 재암호화 도구는 없습니다. 쓰는 기능이 생기기 전까지 개인키를 저장하지 않게 할지는 정하지 않았습니다.
- 소셜 로그인: 비밀번호로 가입한 계정에 나중에 소셜 로그인을 붙이는 기능은 없습니다. 이 규칙 이전에 연동된 계정(비밀번호 + Google)은 두 방법 모두 계속 로그인됩니다. 서버는 PKCE를 필수로 요구하지 않고 `state`를 브라우저에 묶지 않습니다(FE가 `state`와 PKCE를 확인. 세 제공자 같음). 제공자 쪽 이메일이 바뀌어도 `users.email`은 그대로입니다. `redirect=true`(302로 제공자에 보내기)와 개발용 `GET` 콜백 경로는 남아 있습니다(운영에서 `GET` 콜백은 404). 이메일 검사가 연동 확인보다 먼저라, 이미 연동된 사용자도 제공자에서 이메일 제공 동의(GitHub은 이메일 권한)를 철회하면 400 `OAuth email is required`, Google·GitHub이 이메일을 인증되지 않았다고 알리면 400 `OAuth email is not verified`로 로그인이 막힙니다. 보이지 않는 서식 문자나 소문자로 바꾸면 ASCII가 되는 문자(켈빈 기호 U+212A 등)가 든 제공자 이메일은 다른 계정과 같게 읽히거나 똑같아 보이므로 502로 받지 않습니다.
  - 네이버: 이메일 인증 여부를 알려 주지 않으므로, 네이버로 만든 계정의 이메일은 그 사람이 소유하지 않은 주소일 수 있습니다. 그런 계정은 다른 로그인 방법과 연동되지 않고, 그 주소의 진짜 주인은 같은 이메일로 새로 가입할 수 없습니다(이메일 가입은 400 `Email already registered`, Google·GitHub 로그인은 409 `This email is already used by another sign-in method. …`). 남의 주소로 만든 네이버 계정을 찾거나 지우는 관리 도구는 없습니다. 네이버는 기존 OAuth 2.0 엔드포인트(`/oauth2.0/*`)를 쓰고 PKCE를 보내지 않습니다(네이버 OIDC 엔드포인트는 쓰지 않음). 그래서 콜백 주소의 `code`·`state`가 새면(위 CloudFront 로그) 코드가 만료되기 전에는 누구나 그 값으로 로그인을 마칠 수 있습니다(`state`를 브라우저 쿠키에 묶는 처리는 하지 않음). 또 네이버 이메일은 사용자가 정하는 값이므로, 아무 주소나 네이버 연락처 이메일로 넣어 보면 그 주소가 어떤 방법(비밀번호·Google/GitHub·네이버)으로 가입됐는지 409 문구로 알 수 있습니다(이메일 가입도 이미 있는 주소인지는 알려 줌).
  - GitHub: 로그인에 받은 액세스 토큰은 저장·로그하지 않고 버리기만 하고 폐기 API(`DELETE /applications/{client_id}/token`)는 부르지 않습니다. 새 OAuth App은 토큰이 8시간 뒤 만료되므로 OAuth App 설정의 "Expire user access tokens"를 켜 둡니다(끄면 토큰이 1년 동안 쓰지 않아야 자동 폐기됨). 이메일 목록(`/user/emails`)은 첫 100개만 보고 그 안에 기본(primary) 이메일이 없으면 400 `OAuth email is required`입니다. `users.noreply.github.com` 주소도 기본·인증 이메일이면 계정 이메일로 씁니다(따로 막지 않음). 사용자가 이메일 권한을 뺀 경우와 GitHub 레이트 리밋의 403을 구분하지 않아 둘 다 400 `OAuth email is required`입니다. 토큰 요청 오류의 HTTP 상태와 PKCE 불일치 오류 이름은 GitHub 문서에 없어, 2xx·4xx 응답의 `bad_verification_code`·`redirect_uri_mismatch`·`invalid_grant`(400 `Invalid or expired OAuth authorization code`)와 `unverified_user_email`(400 `OAuth email is not verified`)만 사용자 쪽 400으로 보고, 3xx·5xx는 `error` 내용과 관계없이 502로 봅니다. GitHub의 인증(verified) 표시는 한 번 인증한 기록이라 다시 확인하지 않습니다: 예전에 그 주소를 쓰던 사람(퇴사·도메인 만료 등)의 GitHub 계정에 그 주소가 인증된 기본 이메일로 남아 있으면, 지금 주인이 Google로 만든 같은 이메일의 계정에 연동될 수 있습니다(반대로 그런 GitHub 계정으로 먼저 만든 계정에는 지금 주인의 Google 로그인이 연동됨). 연동 전에 기존 방법으로 다시 로그인하게 하는 처리는 하지 않았습니다.
  - Google 계정의 이메일이 바뀌면 그 계정의 Google 연동 이메일(로그인할 때마다 갱신)이 계정 이메일과 달라져, 같은 이메일의 GitHub 로그인이 그 계정에 연동되지 않고 409가 됩니다(잘못 붙는 일은 없음. GitHub 기본 이메일이 바뀐 경우도 반대로 같음).
  - 예전에 쓰던(지금은 로그인 경로가 없는) 제공자의 연동 행이 개발 DB에 남아 있으면 지우지 않고 그대로 둡니다(로그인·연동 확인에 쓰지 않고, `GET /api/v1/users/me`의 `oauth_providers`에는 이름이 나오지만 FE는 모르는 이름을 무시함. 마이그레이션 없음). 그 제공자로만 만든 비밀번호 없는 개발용 계정은 더 이상 로그인할 수 없고, 같은 이메일의 GitHub·Google 로그인도 409(다른 방법으로 가입한 이메일)입니다. 필요하면 그 계정을 지우고 다시 가입합니다.
  - GitHub·네이버의 실제 동작(로컬 콜백 주소 허용, 오류 응답 본문·상태 코드, 승인 화면)은 실제 서버로 확인하지 못했습니다(테스트는 가짜 응답만 씀. GitHub은 OAuth App을 만들고 키를 넣은 뒤 따로 확인). 서비스를 열기 전에 위 "배포 후 확인"으로 한 번 확인합니다.
- DB: 연결 풀이 아니라 요청마다 새 연결을 엽니다(RDS에서는 매번 TLS·인증 절차). DB 접속 자체가 실패하면(DB 중단, DB 쪽 연결 수 초과) 503이 아니라 500입니다. 철회·만료된 공유 링크와 지난 직무 비교·커리큘럼을 지우는 정리 작업, 목록의 페이지 나누기는 없습니다(목록은 200개까지). RDS Proxy를 앞에 둔 구성에서 앱의 세션 시간 제한이 그대로 걸리는지는 확인하지 않았습니다.
- 마이그레이션의 잠금: 13(쓰지 않는 인덱스·표 삭제)과 `users`를 고치는 04·09는 `users` 표에 배타 잠금(`ACCESS EXCLUSIVE`)이 필요하고, 실행기에는 잠금 대기 제한이 없습니다. 그 DB에 `users`를 읽는 트랜잭션이 열려 있으면(`pg_dump`, 운영자가 열어 둔 `psql` 등) 마이그레이션이 그 뒤에서 기다리고, 그동안 `users`를 읽는 요청(로그인한 모든 요청)이 다시 그 뒤에 줄을 섭니다. 지금 BE는 5초 뒤 503으로 답하지만, 마이그레이션 태스크를 실행하는 시점에 아직 떠 있는 이전 버전 BE는 잠금 제한이 없어 끝날 때까지 멈춥니다. 실행하기 전에 `pg_stat_activity`로 오래 열린 트랜잭션이 없는지 확인하고 요청이 적은 시간에 실행하며, 몇 초 안에 끝나지 않으면 취소한 뒤 다시 실행합니다(13은 한 트랜잭션이라 취소하면 통째로 롤백).
- AI 서비스: BE는 요청마다 검토된 공고·학습자료 전체를 AI로 보냅니다(캐시 없음). `AI_MAX_CONCURRENCY`는 태스크 전체 상한이고 한 계정은 그 가운데 동시에 2자리까지만 쥐므로(분당 30번), 계정 두 개면 기본 4자리를 모두 쥘 수 있습니다(WAF의 IP별 규칙과 감사 로그 `event=corpus_budget_denied`로 봄). AI 서비스의 `/docs`는 켜져 있습니다(AI는 공개 로드밸런서에 붙이지 않음). AI의 `GET /v1/market/catalog`는 남아 있지만 지금은 BE·FE 어디에서도 부르지 않습니다. `POST /v1/market/snapshots`에는 요청 전체의 계산량 상한이 없어, 서비스 토큰을 가진 쪽이 계약 상한 안에서 일부러 만든 요청 하나가 CPU 약 286초를 씁니다([ai/docs/CAREER_AI_SERVICE.md](../ai/docs/CAREER_AI_SERVICE.md)). 로컬 Qwen 실행과 `requirements-gpu.txt`는 이번에 확인하지 않았습니다.
- AI 업그레이드: 결합 문자가 30개 넘게 이어진 구간을 자르는 정규화 변경 때문에, 그런 구간이 든 공고·학습자료가 이미 저장된 DB에서는 그 공고가 들어가는 공고 목록·직무 비교가 409가 될 수 있습니다(일부러 만든 입력에서만 확인된 경우). 기존 DB에 새 AI를 올리기 전에 [BE/README.md](../BE/README.md)의 "결합 문자 점검"으로 한 번 확인합니다. 자동으로 고쳐 주는 마이그레이션은 없습니다.
- 시장 통계: 출처는 한 곳이고 공고 번호는 사람이 모읍니다. 수집 코드는 robots.txt를 읽지 않으므로 수집 전에 사람이 확인합니다([BE/README.md](../BE/README.md) "직무별 채용 시장 통계"). 공고 한 건을 읽는 30초 상한은 본문 데이터가 올 때만 재므로, 응답 머리말을 아주 천천히 보내는 서버에는 걸리지 않습니다(읽기 한 번마다의 15초 제한만 있어, 머리말을 한 줄씩 5초마다 보내는 시험 서버는 보내는 동안 계속(75초) 수집을 붙잡았음). 전화번호·이메일 가리기는 `/`·`_`·`~`로 나눈 번호, 대표번호, `(at)` 표기, `@` 앞이 한글인 주소를 잡지 않습니다.
- FE: Pretendard 웹폰트는 CDN에서 받습니다(자체 호스팅·SRI 없음). 자동 테스트가 없어 CI는 lint·타입 검사·빌드와 `dist` 검사만 합니다. 포트폴리오 화면의 대화는 모의 응답입니다.
- CI: Strix 보안 스캔 워크플로(`.github/workflows/main.yml`)는 PR마다 돌지만 저장소 Secrets에 `STRIX_LLM`·`LLM_API_KEY` 중 하나라도 없으면 스캔을 건너뛰고 성공으로 끝납니다. Secrets를 등록하기 전에는 실제 스캔이 돌지 않는 상태이고, 등록해 쓸지 워크플로를 지울지는 정하지 않았습니다.
- 설정 검사: 운영 설정 검사·범위 검사 오류와 없는 수준 이름의 `LOG_LEVEL`(예: `verbose`), 형식이 틀린 `HOLDER_KEY_ENCRYPTION_KEY`, AI의 잘못된 `AI_MAX_BODY_BYTES`는 traceback 없이 한 줄(종료 코드 1, 시장 통계 배치의 `LOG_LEVEL`은 오류 한 줄과 종료 코드 2)로 끝납니다. 숫자가 아닌 `DB_PORT`는 접속할 때마다 실패합니다(운영 BE는 시작 DB 점검에서 `ValueError: DB_PORT and DB_CONNECT_TIMEOUT must be integers`로 끝남). WAF 속도 값은 부하 시험으로 정한 값이 아닙니다.
- AWS 배포: 도메인 없는 기본 구성에서 Google 로그인은 테스트 상태(등록한 테스트 사용자만)로 두고, 네이버가 CloudFront 기본 도메인으로 검수를 통과하는지는 확인하지 못했습니다. CloudFront·VPC 원본·내부 ALB·Service Connect TLS·WAF의 실제 동작은 로컬 흉내로만 확인했고, CI는 이미지를 운영 모드로 띄워 보지 않으며, Dockerfile은 패키지 해시 검사와 기본 이미지 다이제스트 고정을 하지 않습니다([deploy/README.md](README.md) "받아들이는 잔여 위험").
