# 3차 실험 설계안 v1: VC 실검증 대 저장된 "verified" 표시

작성일: 2026-10-14
상태: **권장안(E1–E5)으로 실행 완료 (2026-10-14)**. R0 승인 후 test 448건 생성. 결과: `outputs\VC_AI_STUDY_03_20261014\NOTION_3차실험_결과.md`.
선행 자료: `paper_experiment2_design_v1.md`, 2차 결과(`outputs\VC_AI_STUDY_02_20261013`), 1차 묶음(`outputs\VC_AI_MAIN_STUDY_01_20261012`).

## 0. 이 실험이 필요한 이유

2차 실험은 기록을 고를 때 **DB에 저장된 검증 결과**(`verification.status = "verified"` 등)만 읽었다. 실행 시점에 서명을 다시 검증하지 않았다(`verification_basis: "reported_checks_only"`). 모델에는 파싱된 본문만 전달됐다.

따라서 2차의 V 조건은 "일반 DB에 검증 상태 칸을 두고 거른 시스템"과 구별되지 않는다. 2차가 보여준 것은 **선별 정책의 효과**이지 **VC의 효과**가 아니다.

VC가 일반 DB보다 나은 지점은 하나다.

> 저장된 내용이나 "verified" 표시가 바뀌어도, 서명된 원본으로 다시 검증하면 드러난다.

3차 실험은 이 차이를 직접 측정한다. **저장된 표시와 내용을 강제로 바꾼 상황**에서, 그 표시를 믿는 시스템과 매번 서명을 검증하는 시스템이 어떻게 달라지는지 본다.

## 1. 확인한 재료

| 재료 | 상태 | 위치 |
|---|---|---|
| 모든 기록의 서명된 원본(compact JWS) | 보존됨 | 1차 `bundle.json` → verification.records[].raw_ref.compactJws |
| 공개키·신뢰 목록·폐기 목록 스냅샷 | 보존됨 | 같은 파일 public_snapshots (did-documents, trust-registry, revocation-list) |
| 검증 코드 | 있음 | `VC/src/verify/pipeline.ts`의 `verifyAndNormalize`, `checks.ts` |
| 서명용 비밀키 | **보존 안 됨** | 의도된 상태. 변조자는 다시 서명할 수 없다는 위협 모델과 일치 |

## 2. 연구 질문

| ID | 질문 |
|---|---|
| RQ1 | 저장된 "verified" 표시가 위조되면, 표시를 믿는 시스템과 VC 실검증 시스템의 환각은 어떻게 달라지는가 |
| RQ2 | 저장된 기록 내용이 변조되면(서명은 그대로), 각 시스템은 거짓을 얼마나 내보내는가 |
| RQ3 | 참인 기록의 표시가 "실패"로 강제되면, 각 시스템은 참인 정보를 얼마나 잃는가 |
| RQ4 | 부적격 기록을 지우지 않고 플래그를 붙여 넘긴 뒤 마지막에 차이를 대조하면, 환각 감소와 정보 보존을 함께 얻는가 |
| RQ5 | 변조가 없을 때 2차 결과가 그대로 재현되는가 (조작 점검) |

## 3. 위협 모델

- 변조자는 **백엔드 DB의 파싱된 기록**을 고칠 수 있다. 본문(description)과 검증 표시(verification.status, checks)가 대상이다.
- 변조자는 발급자의 비밀키가 없으므로 **서명된 원본(JWS)은 고칠 수 없다**.
- 시스템마다 무엇을 진실의 기준으로 삼느냐가 다르다(4절).

이 가정을 논문에 명시한다. 키 탈취나 발급자 자체의 거짓 발급은 범위 밖이다.

## 4. 시스템 (조건)

모든 시스템은 같은 프롬프트, 같은 모델, 같은 직렬화 형식을 쓴다. 다른 것은 **무엇을 근거로 기록을 고르고, 어떤 본문을 넣느냐**뿐이다.

| ID | 이름 | 상태 판단 근거 | 넣는 본문 | 부적격 기록 처리 |
|---|---|---|---|---|
| P | 일반 문서 | 판단 안 함 | DB 본문 | 모두 포함 |
| D | DB 표시 신뢰 (비VC) | DB의 `verification.status` | DB 본문 | 제거 |
| VC | VC 실검증 | 실행 시점 `verifyAndNormalize` 재검증 | **서명된 원본에서 추출한 본문** | 제거 |
| VC-F | VC 실검증 + 플래그 + 사후 대조 | 실행 시점 재검증 | 서명된 원본 본문 | 플래그를 붙여 포함, 생성 후 대조 알고리즘이 주장별로 표시 |
| D-F (선택) | DB 표시 + 플래그 + 사후 대조 | DB 표시 | DB 본문 | VC-F와 같은 방식 (비VC 대응 조건) |

- D와 VC의 차이가 이 실험의 핵심 대비다. 변조가 없으면 둘의 입력은 같아야 한다(RQ5).
- 플래그 문구는 모든 플래그 조건에서 동일하게 쓴다. 예: `"검증 상태": "검증 실패(폐기됨)"`, `"검증 상태": "만료됨"`.
- 사후 대조 알고리즘은 **시스템이 아는 정보만** 쓴다(검증된 원본 본문, 검증 결과). 실험용 정답(gold)은 쓰지 않는다.

## 5. 변조 시나리오 (DB에만 적용, 원본 JWS는 그대로)

| ID | 시나리오 | 변조 내용 | 대상 사례 | 기대 |
|---|---|---|---|---|
| S0 | 변조 없음 | 없음 | 48 | D = VC = 2차 V (재현) |
| S1 | 상태 위조 | 부적격 기록(위조·폐기·만료·비신뢰)의 DB 표시를 `verified`로 강제 | 부적격 32 | D는 거짓 기록을 받아들임. VC는 재검증으로 걸러냄 |
| S2 | 내용 변조 | 적격 기록의 DB 본문을 바꿈. 구현 수 f1을 1차 반사실 값으로(예: 4개 → 13개). 표시는 `verified` 유지 | 48 | P·D는 변조된 수치를 사용. VC는 원본 본문을 써서 영향 없음 |
| S3 | 표시 하향 | 참인 적격 기록(점검 수 f2)의 DB 표시를 `revoked`로 강제 | 48 | D는 참인 정보를 잃음. VC는 재검증으로 유지 |

- S2는 구현 수(f1)를 쓴다. 1·2차에서 한 번도 오염되거나 제거되지 않은 항목이라, 변조 효과만 깨끗하게 보인다. 반사실 값은 이미 데이터에 있다.
- S3은 점검 수(f2)를 쓴다. 같은 이유다.
- 변조는 복사본 DB 스냅샷에만 적용한다. 1·2차 원본 파일은 건드리지 않는다.

## 6. 실행 규모

| 시나리오 | 조건 | 사례 | 생성 |
|---|---|---:|---:|
| S0 | P, D, VC, VC-F | 48 | 최대 192 |
| S1 | D, VC, VC-F | 32 | 96 |
| S2 | P, D, VC, VC-F | 48 | 192 |
| S3 | D, VC, VC-F | 48 | 144 |

- 입력이 바이트 단위로 같은 실행은 결과도 같으므로(greedy, 2차에서 96/96 재현 확인), 같은 입력은 **한 번만 생성하고 결과를 공유**한다. 공유 여부는 manifest에 기록한다.
- 예상 고유 생성 수는 약 350–450건, GPU 기준 약 30분이다. D-F를 넣으면 약 100건이 늘어난다.
- 모델과 설정은 2차와 같다(Qwen2.5-1.5B, greedy, seed 42, 출력 256토큰).

## 7. 측정

### 7-1. 시스템 수준 (모델과 무관, 결정적)
- **변조 탐지율:** 변조된 기록 중 시스템이 잡아낸 비율. VC는 100%, D·P는 0%가 기대된다. 이 지표가 "VC를 써야 하는 이유"의 1차 근거다.
- **오탐률:** 변조 없는 기록을 실패로 판단한 비율. 기대값은 0%다.

### 7-2. 답변 수준 (2차 판정기 재사용 + 플래그 처리 추가)

| 지표 | 정의 |
|---|---|
| **표시 없는 거짓 단정률** (주 지표) | 기준 3슬롯 중 틀린 값을 플래그 없이 사실로 단정한 비율 |
| 보존율 (표시 무관) | 정답이 표시와 함께라도 나온 비율 |
| 보존율 (표시 없음) | 정답이 검증된 사실로 나온 비율 |
| 변조값 전파 | S2에서 변조된 구현 수가 답변에 나온 비율 |
| 손해 점수 | 추천 가중치(F 1.0, S 1.0, O 0.8, M 0.5, L 0.3). 플래그가 붙은 거짓은 L과 같은 0.3으로 계산 (지원자가 볼 수 있음) |

- 플래그가 붙은 거짓을 0.3으로 두는 규칙은 사전 고정한다. 동일 가중치와 손익분기를 함께 보고한다.

### 7-3. 사전 지정 대비

| 대비 | 시나리오 | 답하는 질문 |
|---|---|---|
| VC − D | S1 | 표시 위조에 대한 내성 (RQ1) |
| VC − D, VC − P | S2 | 내용 변조에 대한 내성 (RQ2) |
| VC − D | S3 | 표시 하향에 대한 내성, 정보 보존 (RQ3) |
| VC-F − VC | S0–S3 | 플래그 + 사후 대조의 효과 (RQ4) |
| D − VC | S0 | 0이어야 함 (RQ5, 조작 점검) |

통계 처리는 2차와 같다. 사례군 8개를 독립 단위로 두고, 사례군 단위 bootstrap 95% CI와 방향 일치 사례군 수를 보고한다.

## 10. 한계 (미리 적어 둠)

- 연구용 테스트 키와 fixture DID를 쓴다. 실제 기관 발급이나 운영 신뢰 체계가 아니다.
- 위협 모델은 DB 수준 변조로 한정한다. 키 탈취나 발급자 자체의 거짓 발급은 다루지 않는다.
- S2에서 VC가 영향을 받지 않는 것은 설계상 당연한 결과다. 의미는 크기가 아니라, P·D에서 변조가 얼마나 그대로 답변까지 전달되는지에 있다.
- 2차와 같은 합성 지원자 8명, 1.5B 모델 하나를 쓴다. 탐색적 실험이다.
